# 금융뉴스브리핑 워크플로우 설명

> 이 문서는 `mini_project2.json` 워크플로우가 **왜 이렇게 구성되어 있고, 각 노드가 정확히 뭘 하는지**를 사람이 읽을 수 있게 정리한 것입니다.
> 아래 설명은 현재 적용 중인 최종 설계 기준입니다 (LLM 기반 중복판단 `is_duplicate` 추가 작업이 진행 중이라, 지금 이 문서와 실제 n8n 캔버스가 100% 일치하지 않을 수 있습니다 — 진행 상황은 대화 맥락 참고).

## 1. 한 장 요약

```
[스케줄 08:30] ┐
[수동 실행]     ┴─▶ RSS(CNBC) ▶ RSS(MarketWatch) ▶ RSS(한국경제)   ← 3개를 순서대로만 연결(장애 시 다음 피드로 계속)
                                                        │
                                                        ▼
                                            오늘기사_소스태깅  (오늘 KST 기사만, source 태깅)
                                                        │
                                                        ▼
                                            발송이력_조회  (구글시트 '발송이력' 탭 전체 읽기)
                                                        │
                                                        ▼
                                            중복제거  (unique_key로 이미 보낸 기사 제외) ← REQ-03, LLM 호출 이전
                                                        │
                                                        ▼
                                            금융키워드필터  (연예/스포츠/날씨 등 명백히 무관한 것만 제외) ← REQ-04
                                                        │
                                                        ▼
                                            기사목록_조합  (오늘 남은 기사 전체를 번호 매긴 목록 하나로 묶음)
                                                        │
                                                        ▼
                                 기사요약_중요도분류 (AI Agent + Gemini + Structured Output Parser)
                                     → 기사 개수와 같은 길이의 JSON 배열 1개 반환 (호출은 실행당 1번)
                                                        │
                                                        ▼
                                            검증_필드조합  (LLM 응답 검증 + 안전 기본값 + 최종 필드 조합)
                                                        │
                                                        ▼
                                            중요도필터  (importance >= 4만 남김) ← REQ-05
                                                        │
                                        ┌───────────────┴───────────────┐
                                        ▼                               ▼
                              디스코드메시지생성                  발송이력_기록
                          (0건이어도 "조용합니다" 메시지 생성)      (구글시트에 append)
                                        │
                                        ▼
                              디스코드_브리핑발송  (메시지 1개로 전송)
```

## 2. 트리거 — REQ-02

- **스케줄 트리거**: cron `30 8 * * *` → 매일 08:30에 자동 실행. (n8n 인스턴스의 타임존이 `Asia/Seoul`로 맞춰져 있어야 한국시간 08:30이 됩니다. 인스턴스 설정에서 확인 필요)
- **수동 실행 트리거**: 테스트용. 캔버스에서 바로 눌러서 전체 흐름을 즉시 실행해볼 수 있음. 두 트리거 모두 같은 다음 노드(RSS 수집)로 연결되어 있어서, 어느 쪽으로 실행하든 로직은 동일합니다.

## 3. RSS 수집 — REQ-01

3개 노드(`RSS 수집 - CNBC Finance`, `RSS 수집 - MarketWatch`, `RSS 수집 - 한국경제 증권`)를 **Merge 노드 없이 그냥 순서대로 체인 연결**했습니다.

- 왜 체인으로? RSS Feed Read 노드는 입력 데이터를 안 쓰고 그냥 자기 URL을 다시 가져오기만 하므로, 순서대로 연결해도 각자 독립적으로 동작합니다. 대신 "다음 노드로 넘어가려면 앞 노드가 실행을 끝내야 한다"는 순서 보장을 공짜로 얻습니다.
- 각 RSS 노드는 `alwaysOutputData: true`, `onError: continueRegularOutput`으로 설정되어 있음 → **한 피드가 타임아웃/장애가 나도 워크플로우가 멈추지 않고 나머지 피드로 계속 진행**됩니다 (REQ-01이 명시한 "안전장치" 요구사항).

## 4. 오늘기사_소스태깅

다음 3개 피드를 `$('노드이름').all()`로 직접 참조해서 하나로 합치고, 두 가지 일을 합니다.

1. **오늘(KST) 기사만 남기기**: `pubDate`를 KST로 환산해서 오늘 날짜와 다르면 버림.

|미국 기사 발행 시각(ET, 전날 기준)|KST 환산|오늘 브리핑에 포함?|
|---|---|---|
|9:30am~11:00am (개장 직후)|전날 22:30~24:00 KST|❌ **빠짐** (아래 이유)|
|11:00am~4:00pm (장중 대부분+마감)|오늘 00:00~05:00 KST|✅ 포함|
|4:00pm~7:30pm (애프터마켓)|오늘 05:00~08:30 KST|✅ 포함|


 마감/애프터마켓(11am~7:30pm ET, 즉 그날의 최종 결과·수익률·실적발표 같은 브리핑에 제일 중요한 내용)은 걸림.


2. **source 태깅**: `link`에 어떤 도메인이 들어있는지 보고 `cnbc`/`marketwatch`/`hankyung`을 붙임 (매체별로 Set 노드를 따로 두지 않고, 이미 있는 URL 정보에서 바로 뽑아내는 방식 — 노드 수를 줄임).

각 RSS 노드를 `try/catch`로 감싸서, 특정 피드가 아예 실행 자체를 못 했어도(장애) 그 피드만 건너뛰고 나머지는 정상 처리합니다.

## 5. 발송이력_조회 + 중복제거 — REQ-03

- `발송이력_조회`: 구글시트 `발송이력` 탭의 모든 행을 읽어옴 (`alwaysOutputData: true` → 시트가 비어있어도(첫 실행) 에러 없이 빈 배열로 처리됨).
- `중복제거`: 이 노드의 **직접 입력은 시트에서 읽어온 발송이력**이고, **오늘 수집한 기사는 `$('오늘기사_소스태깅').all()`로 조상 노드를 참조**해서 따로 가져옵니다.

**고유값(unique_key) = 정규화된 기사 URL**을 씁니다.
- 이유: CNBC/MarketWatch는 `<guid>`가 있지만 한국경제 피드에는 `<guid>` 태그 자체가 없어서, 3개 피드 전체에 공통으로 존재하는 필드가 `link`뿐이었습니다.
- 정규화(`normalizeUrl`): `?` 뒤 쿼리스트링과 끝의 `/`를 제거. MarketWatch는 URL 끝에 `?mod=mw_rss_topstories` 같은 트래킹 파라미터가 붙기 때문에, 정규화 없이 그냥 비교하면 같은 기사가 다른 URL로 인식되어 중복 제거가 새고 이력에도 매번 다르게 쌓입니다.
- `seenInThisRun`: 같은 실행 안에서 우연히 같은 URL이 두 번 들어온 경우도 방지하는 보조 장치.
- 이 필터는 **LLM 호출(`기사요약_중요도분류`) 이전**에 있어서, 이미 보낸 기사는 애초에 요약 비용조차 들지 않습니다 (REQ-03 요구사항 그대로).

## 6. 금융키워드필터 — REQ-04

**배제(exclude) 방식**입니다: "연예/스포츠/날씨 등 명백히 무관한 신호가 있으면 제외, 나머지는 통과."

- 처음엔 반대로 "금융 키워드가 있어야 통과"하는 포함(include) 방식으로 만들었었는데, 실제 테스트에서 CNBC/MarketWatch의 관용적인 영어 헤드라인(예: "Michael Burry bets against rally", "Polymarket in talks for fundraising round")에는 `stock`/`market` 같은 정확한 키워드가 없어서 부당하게 걸러지고, 한국경제 헤드라인은 거의 항상 "코스피"/"증시"가 박혀 있어 다 통과하는 **언어 편향**이 발견되어 방식을 바꿨습니다.
- 판단 근거: CNBC Finance / MarketWatch Top Stories / 한국경제 증권은 이미 금융 전문 섹션이라 원래 무관 기사 비율이 낮음 → "관련 있어야 통과"보다 "명백히 무관해야 제외"가 recall(누락 방지) 관점에서 더 안전.
- **LLM 호출 앞에 배치한 이유**: 이 필터는 비용이 0(Code 노드)이라 순수 이득이고, 설사 애매한 잡음 기사가 통과해도 뒤에 있는 LLM이 `category=기타`/`importance 1~2`로 판정하면 어차피 발송 대상(4+)에서 자동 제외되는 **이중 안전판**이 있습니다.

## 7. 기사목록_조합 — 비용 최적화

기사를 한 건씩 LLM에 넣으면 **기사 수 = API 호출 수**가 되어버립니다 (실제 테스트에서 18건 나왔을 때 18번 호출됨 — 과다 사용 문제로 지적받은 부분).

그래서 오늘 남은 기사 전체를 번호가 매겨진 텍스트 목록 하나로 합쳐서, 딱 **1개의 아이템**으로 만든 다음 LLM에 통째로 넘깁니다. 이러면 워크플로우 1회 실행 = LLM 호출 1회로 고정됩니다.

## 8. 기사요약_중요도분류 (AI Agent) — REQ-05

- **AI Agent** (`@n8n/n8n-nodes-langchain.agent`) + **Google Gemini Chat Model** (언어모델) + **Structured Output Parser** (JSON 강제) 세 노드가 한 세트로 동작합니다. Agent 노드가 실제 실행 주체이고, 나머지 둘은 "어떤 모델을 쓸지"/"출력을 어떤 JSON 모양으로 강제할지"를 꽂아주는 서브 노드입니다.
- System Message에 REQ-05가 요구하는 **중요도 판정 기준(1~5)**을 그대로 명시했습니다.
- 프롬프트에서 "입력 기사 개수와 정확히 같은 길이의 배열로, i번째 항목은 반드시 i번째 기사의 결과"라고 강하게 지시합니다 — 배치 처리라서 순서가 곧 매칭 기준이기 때문에 이 지시가 핵심입니다.
- (진행 중인 개선) 같은 사건을 시간대별로 반복 보도한 속보들(예: 코스피 급등을 장중→마감까지 6번 보도)을 텍스트 유사도로 걸러보려 했으나 실패 — 매번 다른 숫자/디테일이 강조되는 기사라 문자 비교로는 "같은 사건"이라는 걸 못 잡았습니다. 그래서 이 판단을 LLM에 맡기기로 하고, 각 기사 결과에 `is_duplicate` 필드를 추가해서 "같은 사건의 반복 속보면 최신 것만 정상 분석하고 나머지는 `true`로 표시"하도록 프롬프트를 확장하는 중입니다. 추가 API 호출 없이(이미 배치로 한 번에 보내고 있으므로) 해결됩니다.
- **AI Agent + Output Parser를 같이 쓰면 실제 응답이 `output`이라는 키로 한 번 더 감싸져서 나옵니다** (`$json.output.summary`처럼 접근해야 함) — 이건 n8n의 알려진 동작이라 다음 단계 코드에 이미 반영되어 있습니다.
- `onError: continueErrorOutput`: LLM 호출 자체가 실패해도(네트워크 오류, 쿼터 초과 등) 워크플로우가 멈추지 않고 에러 출력 경로로 다음 노드에 도달합니다.

## 9. 검증_필드조합 — 안전판

LLM 응답을 무조건 믿지 않고, 아래를 검증합니다.

| 검증 항목 | 실패 시 처리 |
|---|---|
| 응답이 배열이고 길이가 원본 기사 수와 같은가 (`arrayOk`) | 다르면 **이 실행의 모든 기사**를 안전 기본값 처리 (순서가 꼬였을 수 있어, 잘못 짝짓기보다 전부 보수적으로 처리) |
| `category`가 7개 허용값 중 하나인가 | 아니면 `기타` |
| `summary`가 비어있지 않은 문자열인가 | 아니면 `(요약 실패 - 원문 확인 필요)` |
| `importance`가 1~5 정수인가 | 아니면 `1` (가장 안전한 값 — 4+ 발송 대상에서 자동 제외됨) |

위 중 하나라도 실패하면 `needs_review = true`로 표시해서, 나중에 시트에서 "이 기사는 LLM 응답이 이상했다"를 감사(audit)할 수 있게 남깁니다.

원본 기사 정보(`title`, `link`, `unique_key`, `source`, 수집일)는 LLM 응답이 아니라 `$('금융키워드필터').all()`(조상 노드)에서 그대로 가져옵니다 — LLM은 순수하게 summary/category/importance/is_duplicate 판단만 하고, 사실 정보(제목/링크)는 우리가 직접 관리한다는 원칙입니다.

## 10. 중요도필터 — REQ-05

`importance >= 4`인 것만 남깁니다. `alwaysOutputData: true`를 켜서, 0건이어도(모두 3 이하) 빈 배열이 그대로 다음 노드로 확실히 전달되게 해뒀습니다.

## 11. 디스코드메시지생성 — REQ-06

**항상 정확히 1개의 아이템(메시지 문자열)을 반환**하는 것이 이 노드의 핵심 역할입니다.

- 기사가 1건 이상이면: 중요도 높은 순으로 정렬 → `📈 오늘의 금융 브리핑 (날짜)` 형식으로 번호/카테고리/제목/요약/링크를 하나의 문자열로 합침.
- 기사가 0건이면: `📭 오늘은 중요도 4 이상인 기사가 없습니다 (시스템은 정상 작동 중입니다)` 메시지를 생성 — **"조용한 것"과 "고장난 것"을 사람이 구분할 수 있게 하는 REQ-06의 요구사항**을 이렇게 처리했습니다.
- 메시지가 1900자를 넘으면 자르고 "일부만 표시" 안내를 붙입니다 (디스코드 메시지 2000자 제한 대비 — ponytail: 기사 수가 정말 많아지면 여러 메시지로 쪼개는 로직으로 업그레이드 필요).

## 12. 발송 + 이력 기록 — REQ-06 / REQ-07

`중요도필터`의 출력 하나가 **두 곳으로 동시에 연결**됩니다.

- `디스코드메시지생성` → `디스코드_브리핑발송`: 웹훅으로 메시지 1개 전송.
- `발송이력_기록`: 같은 데이터를 구글시트 `발송이력` 탭에 그대로 append. 컬럼은 `sent_date, unique_key, title, link, source, category, importance, summary, needs_review` — 필드명이 시트 헤더와 정확히 같아서 `autoMapInputData` 모드로 자동 매핑됩니다.

이 두 동작이 **같은 입력(중요도 4+ 기사)**을 쓰기 때문에, "디스코드에 보낸 기사 = 시트에 기록되는 기사"가 항상 일치합니다.

## 13. 알아두면 좋은 설계 판단 근거 (요약)

| 결정 | 선택 | 근거 |
|---|---|---|
| REQ-03 고유값 | 정규화된 URL | 3개 피드 중 한국경제에 `guid`가 없어서, 공통으로 존재하는 필드가 URL뿐이었음 |
| REQ-04 필터 위치 | LLM 호출 **앞** | 비용은 0인데(Code 노드), 놓치는 진짜 금융기사는 LLM의 category/importance 2차 판정으로 다시 걸러지는 안전판이 있음 |
| REQ-04 필터 방식 | 포함 → **배제**로 전환 | 실제 테스트에서 포함 방식이 영어 헤드라인에 언어 편향적으로 불리하다는 게 확인됨 |
| LLM 호출 방식 | 기사별 개별 호출 → **배치 1회 호출**로 전환 | 개별 호출 시 기사 수만큼 API를 써서 비용이 과했음 (18건=18회) |
