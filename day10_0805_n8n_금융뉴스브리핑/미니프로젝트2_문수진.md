# 미니프로젝트2 - 금융 뉴스 브리핑 Agent

## 1. 프로젝트 소개

리서치팀원들이 매일 아침 출근 전에 여러 뉴스 사이트를 돌아다니면서 금융 관련 기사를 찾아 읽는다고 한다. 문제는 세 가지였다. 사람마다 보는 매체가 달라서 같은 팀인데도 아는 뉴스가 제각각이고, 기사 대부분이 연예/스포츠라 금융 기사 골라내는 데만 시간이 들고, 어제 읽은 기사를 오늘 또 읽는 일도 반복된다는 것.

그래서 이걸 자동화했다. 매일 아침 8시 30분에 여러 매체의 RSS를 모아서, 금융 관련 기사만 골라 AI가 요약하고 중요도를 매긴 다음, 진짜 중요한 것만 디스코드로 한 번에 보내주는 시스템이다.

## 2. 사용한 것

- **RSS 피드 4개** (미국 매체 2개 + 한국 매체 2개)
  - CNBC Finance
  - MarketWatch Top Stories
  - 한국경제 증권
  - 연합뉴스 경제
- **Google Sheets**: 이미 보낸 기사를 기록해두는 "발송이력" 시트
RSS_발송이력 링크: https://docs.google.com/spreadsheets/d/1ajYqDBYiS5pT93EGS3DGelAHvxo_6y1r0o-mD4kSX_s/edit?usp=sharing
- **n8n**: 전체 자동화 흐름을 짜는 도구
- **Google Gemini**: 기사 요약 + 중요도/카테고리 분류 + 중복 판단
- **Discord Webhook**: 개인 채널로 브리핑 발송

## 3. 전체 흐름

```
RSS 4개 수집 (미국 2 + 한국 2)
  → 1. 오늘 기사만 추리고 어느 매체 건지 태깅, 반복 속보는 초벌로 정리
  → 2. 발송이력 시트와 대조해서 이미 보낸 기사 제외
  → 3. 연예/스포츠/날씨처럼 명백히 무관한 기사만 제외
  → 4. 오늘 남은 기사를 목록 하나로 묶어서
  → 5. Gemini에게 한 번에 통째로 넘겨서 요약 + 중요도 + 카테고리 + 중복여부 판단
  → 6. 응답이 이상하면 안전한 기본값으로 처리
  → 7. 중요도 4 이상만 추려서 디스코드로 한 통에 발송 + 시트에 기록
```

## 4. 단계별로 뭘 했는지

### 1단계. RSS 수집 (CNBC/MarketWatch/한국경제 증권/연합뉴스 경제)

처음엔 후보로 미국 매체 CNBC + Yahoo Finance + 한국경제 이렇게 3개를 생각했는데, Yahoo Finance RSS가 실제로 접속해보니 403(접근 차단)으로 죽어있었다. 그래서 MarketWatch로 바꿨다. 나중에 실제로 돌려보니 한국 쪽이 한국경제 하나뿐이라 이게 죽으면 국내 기사가 통째로 안 들어오는 구조라는 걸 깨닫고, 연합뉴스 경제를 하나 더 추가해서 미국 2개, 한국 2개로 맞췄다. 피드를 여러 개 쓰는 이유가 단순히 커버리지 때문만이 아니라 "한쪽이 장애나도 나머지로 버틸 수 있게" 하는 안전장치이기도 해서, 양쪽 다 최소 2개씩은 맞춰야 한다고 판단했다.

RSS 노드들은 특정 피드가 응답을 못 해도 워크플로우 전체가 멈추지 않고 나머지 피드는 계속 진행되도록 설정해뒀다.

### 2단계. 오늘기사_소스태깅

RSS로 가져온 기사 중 오늘(한국시간 기준) 발행된 것만 남기고, 어느 매체에서 왔는지 링크 주소로 구분해서 표시해뒀다.

테스트하다가 같은 매체(한국경제)가 "코스피 급등"이라는 같은 사건을 시간대별로 속보 6개씩 반복 보도하는 걸 발견 -> 제목 문자 유사도로 잡으려 했는데 실패 ("3.8% 급등", "5% 급등", "4%대 급등"처럼 매번 숫자만 바뀌어 텍스트가 많이 안 겹침) -> 비교하기 전 숫자/기호를 다 지우고 나서 다시 비교 -> 성공

여기에 더해서 한 피드가 한 번에 너무 많이 쏟아지는 것도 막기위해 매체당 최대 30건까지만 가져오게 상한선도 뒀다.

30건만 가져와서 생기는 문제 해결 방법
1. 거르기: 오늘 기사인지 먼저 확인 (아니면 탈락)

|미국 기사 발행 시각(ET, 전날 기준)|KST 환산|오늘 브리핑에 포함?|
|---|---|---|
|9:30am~11:00am (개장 직후)|전날 22:30~24:00 KST|❌ **빠짐** (아래 이유)|
|11:00am~4:00pm (장중 대부분+마감)|오늘 00:00~05:00 KST|✅ 포함|
|4:00pm~7:30pm (애프터마켓)|오늘 05:00~08:30 KST|✅ 포함|

 마감/애프터마켓(11am~7:30pm ET, 즉 그날의 최종 결과·수익률·실적발표 같은 브리핑에 제일 중요한 내용)은 걸림.

2. 정렬: 피드 순서를 안 믿고, 남은 기사를 실제 날짜로 직접 최신순 정렬
3. 반복 속보 정리: 같은 사건 반복 속보면 하나만 남김
4. 자르기: 그러고 나서야 매체당 30건 상한선 적용

### 3단계. 중복제거

구글시트 "발송이력"에 이미 기록된 기사와 대조해서, 이미 보낸 기사는 여기서 걸러낸다.

기사를 구분하는 기준(고유값)을 뭘로 할지가 고민이었다. RSS 표준에는 `guid`라는 고유 식별자가 따로 있는데, 실제로 4개 피드를 다 열어보니 한국경제/연합뉴스 쪽엔 이게 아예 없는 경우가 있었다. 반면 원문 링크(URL)는 4개 피드 전부에 공통으로 있기 때문에, **정규화한 기사 URL을 고유값**으로 쓰기로 했다. 다만 MarketWatch는 같은 기사인데 URL 끝에 `?mod=mw_rss_topstories` 같은 추적용 꼬리표가 붙어서, 이걸 지우고 비교하지 않으면 같은 기사가 매번 다른 URL로 보여서 중복 제거가 새는 문제가 있었다. 그래서 비교 전에 물음표 뒤 쿼리스트링을 지우는 정규화 과정을 거치게 했다.

이 중복 체크는 AI를 부르기 전에 미리 걸러내도록 배치해서, 이미 보낸 기사는 애초에 요약 비용도 들지 않게 했다.

### 4단계. 금융키워드필터

"연예/스포츠/날씨처럼 명백히 무관한 신호가 있을 때만 제외"하는 방식으로 하였다. 어차피 4개 피드 모두 금융/경제 전문 섹션이라 원래 무관한 기사가 드물기 때문에, 이렇게 느슨하게 걸러도 큰 문제가 없다고 판단했다.

이 필터를 AI 호출 앞에 둔 이유는, 비용이 거의 안 드는 필터라 놔둬서 손해볼 게 없고, 설령 애매한 기사가 통과해도 뒤에 있는 AI가 중요도를 낮게 매기면 어차피 발송 대상에서 빠지는 이중 안전장치가 있어서다.

### 5단계. AI 기사요약_중요도분류

처음엔 기사를 한 건씩 AI에 넘겨서 요약을 시켰다. 그런데 테스트해보니 기사가 18건이면 API를 18번 부르는 구조라, 실제로 돌려보고 API 토큰을 너무 소진할 것 같았다. 그래서 그날 남은 기사 전체를 번호 붙인 목록 하나로 합쳐서 AI에게 한 번에 통째로 넘기고, "기사 개수만큼 정확히 같은 길이의 배열로 돌려달라"고 요청하는 방식으로 바꿨다. 이러면 워크플로우 한 번 실행에 AI 호출도 딱 한 번으로 끝난다.

판정 기준(중요도 1~5, 카테고리 7종)은 요청서에 나온 그대로 프롬프트에 명시했다. 그리고 같은 사건 반복 속보 문제를 앞 단계 문자 비교로 완전히 해결하지 못한 부분은, 이미 AI에게 기사를 다 넘기는 김에 "같은 사건 반복 보도면 최신 것만 정상 분석하고 나머지는 중복으로 표시해달라"고 같이 시켜서 처리하기로 했다. 추가 호출 없이 되는 거라 부담이 없었다.

### 6단계. 검증_필드조합

AI에게 한 번에 통째로 데이터를 넘기면 위험한 부분이 있다. AI가 기사 개수랑 다른 길이의 배열을 주면 순서가 꼬여서 요약이 엉뚱한 기사에 붙을 수 있다.

- 응답 배열 길이 = 원본 기사 수 → 맞는지 먼저 확인
- 안 맞으면 → 이번 실행 기사 전체를 안전한 기본값 처리
```Json
{
  "category": "기타",
  "summary": "(요약 실패 - 원문 확인 필요)",
  "importance": 1
}
```
- 중요도 값이 이상하면 → 최하위로 처리 (검증 실패 기사가 실수로 발송되는 일 방지)

### 7단계. 중요도 필터, 디스코드메시지생성, 디스코드_브리핑발송 + 발송이력_기록

- 중요도 4 이상만 디스코드로
- 기사가 5건이면 메시지도 딱 1개
- 중요 기사가 하나도 없는 날엔 "오늘은 중요한 기사가 없습니다, 시스템은 정상 작동 중입니다"라는 메시지를 보내서, 조용한 것과 고장난 것을 구분
- 같은 기사 목록이 구글시트 발송이력에도 쌓여서, 다음날 중복 체크의 기준이 됨

## 5. 하면서 막혔던 부분들

### 미국 기사가 거의 안 들어오는 문제
위에 적은 대로 키워드 필터가 영어 헤드라인에 불리하게 작동하고 있었다. 실제로 브리핑을 열어봤을 때 18건 중 미국 기사가 딱 1개뿐인 걸 보고서야 알았다. 필터 방식을 포함(있어야 통과)에서 배제(없어야 통과)로 뒤집어서 해결했다.

### 같은 사건이 반복해서 뜨는 문제
한국경제가 코스피 급등을 장중부터 마감까지 시간대별로 여러 번 속보 처리하는데, 이게 전부 다른 URL을 가진 "다른 기사"로 인식돼서 브리핑에 같은 얘기가 6번씩 나왔다. 텍스트 유사도로 잡으려다 실패하고(숫자만 다른 기사라 겹치는 글자가 적었음), 숫자를 지우고 비교하는 방식 + AI에게 최종 판단을 맡기는 방식을 같이 써서 해결했다.

### API를 너무 많이 부르는 문제
기사 한 건당 AI 호출 1번 하는 구조였는데, 테스트하다가 한 번 실행에 18번씩 호출되는 걸 보고 "이거 API 다 쓰는 거 아니냐"는 걱정이 들었다. 기사 전체를 하나로 묶어서 한 번만 호출하는 배치 방식으로 바꿔서, 실행 1번 = 호출 1번으로 고정했다.

### 연합뉴스 피드가 유독 많이 쏟아지는 문제
연합뉴스 경제 피드를 추가했더니 다른 매체는 10~50건인데 혼자 120건씩 쏟아졌다. 통신사라 경제 카테고리 전체를 다 담는 피드였기 때문이다. 매체당 가져오는 기사 수에 상한선을 둬서 한쪽으로 쏠리는 걸 막았다.


## 6. 느낀 점

필터를 하나 만들 때마다 "이게 진짜 의도한 대로 동작하나"를 실제 결과로 확인해야 한다는 걸 다시 느꼈다. 키워드 필터도, 중복 제거도 다 설계했다 생각했는데  실제 브리핑을 열어보고서야 문제를 알았다(비슷한 뉴스 브리핑). 그리고 비용과 속도 문제는 처음 설계할 때보다 실제로 숫자(호출 몇 번하는지, item이 얼마나 나오는지)를 보고 나서 최대한 효율적인 설계를 위해 신경써야 한다는 것을 느꼈다.
